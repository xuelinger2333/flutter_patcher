# 工作原理

[English](architecture.md) | **简体中文**

本文解释 flutter_patcher 为什么能工作、为什么值得信任，以及它的边界在哪里。只讲概念，不讲命令用法（见 [CLI 参考](cli-zh.md)）。

## 三个角色

```text
  开发机（CLI）                   App 获取文件的地方                 用户设备（插件）
 ────────────────              ──────────────────────           ──────────────────
 build  → 宿主 + 基线                                            安装的是 build 产出的宿主
 patch  → 一个 .fptc 文件 ──→   任意 HTTPS 服务、自家接口、  ──→  applyPatchBytes / applyPatchFile
 publish → 把 .fptc 写入存储     推送、内嵌、文件选择……             （或 checkUpdate / applyPatch）
                                                                        │
                                                              校验、安装；下次冷启动加载
```

- **开发机**：`dart run flutter_patcher` 构建宿主和基线，再把每次改动生成为一个补丁文件 `<version_code>-<flavor>-<channel>-<abi>.fptc`。`publish` 把它写入存储（本地目录或 S3）；开发时由 `serve` 代劳。**基线存储**保存每个已发布版本的构建记录，只有 CLI 使用。
- **App 获取文件的地方**：插件不负责获取补丁。App 用任何方式拿到文件，交给 `applyPatchBytes` 或 `applyPatchFile` 即可。`checkUpdate` 和 `applyPatch` 只是一个可选的内置下载器，用于放在某个 URL 下的文件。
- **设备**：原生代码逐项校验文件后安装，下次冷启动时加载。

## 宿主：能接收补丁的安装包

补丁只能装到用 `flutter_patcher build` 构建的安装包上，这样的安装包称为**宿主**。与普通的 `flutter build` 相比，宿主多了三样东西：

1. **flutter_patcher 提供的 Flutter 引擎**：在官方引擎的基础上增加了加载补丁所需的能力。CLI 按你的 Flutter 版本下载并校验它，你使用的 Flutter SDK 不会被修改。
2. **一个生成的启动入口**：在你的 `main` 之前运行，负责在冷启动时把补丁装进来。你的源码不会被修改。
3. **宿主策略**：写进安装包的身份信息和一把可选的公钥，包括包名、版本号、flavor、渠道、ABI、补丁策略和 `fptc_key`（补丁公钥；`-` 表示不签名的宿主）。`build` 把它连同编译指纹写入 APK（`assets/flutter_patcher/host-trust.json`）或 Info.plist。安装包签名之后，宿主策略就无法再被改动，设备以它为准判断每个补丁文件。宿主保持构建时的模式：之后再加密钥，只影响此后构建的宿主。

在 Android 上，宿主只在 Android 9（API 28）及以上、App 的主进程中加载补丁；更早的设备上按原包运行。

## 两种补丁策略

Flutter release 包中的 Dart 代码会被编译成机器码。flutter_patcher 提供两种方式更新它：

| | 字节码（默认） | SO |
|---|---|---|
| 补丁内容 | 改动部分编译成的字节码模块 | 整个重新编译的 `libapp.so` |
| 运行方式 | 引擎内置的解释器执行补丁中的代码，未改动的代码仍以机器码运行 | 启动时让 Flutter 改为加载补丁中的 `libapp.so` |
| 平台 | Android、iOS | 仅 Android |
| 补丁体积 | 小，只包含改动 | 大，与 `libapp.so` 相当 |
| 被修改代码的运行速度 | 解释执行，比机器码慢 | 与原版相同 |

iOS 不允许加载下载的机器码，因此只能使用字节码。Android 在 `build` 时选择策略，之后该版本的所有补丁都沿用这个选择。

字节码补丁有两档，由 `patch` 自动选择：**lean** 只包含你自己的包，优先使用；当依赖发生变化，或 lean 档无法满足时，改用 **whole**，把可热更的依赖一起带上。

## 基线：补丁与谁对比

补丁是"当前代码"与"用户手机上的版本"之间的差异，因此必须精确知道后者是什么。`build` 在打包的同时把这个版本的完整事实保存为**基线**：编译结果、源码哈希、依赖、资源、宿主策略，以及构建所用的引擎和工具版本。

`patch` 按 flavor 和版本号（Android 的 versionCode，iOS 的 CFBundleVersion）找到对应的基线，再与当前源码对比，只打包变化的部分。

基线有两条规则：

- **只新增，不覆盖**。同一个版本号如果构建出不同的内容，`build` 会拒绝，而不是悄悄替换已发布版本的记录。要发布新内容，请提升版本号。
- **工具版本固定**。基线记录了构建时使用的引擎和工具版本，以后为这个版本生成补丁时，始终使用同一套。即使 flutter_patcher 之后发布了新的引擎，已上线的版本也能继续打补丁。

由此可以推出：**基线丢失，该版本就无法再生成补丁。**

## 补丁文件

补丁文件（FPTC v1）由 146 字节的文件头和其后的 payload（补丁 ZIP）组成：

| 偏移 | 字节数 | 字段 |
|---:|---:|---|
| 0 | 4 | 魔数 `FPTC` |
| 4 | 2 | 格式版本，1 |
| 6 | 32 | 目标宿主的指纹 |
| 38 | 4 | 序号（uint32，大于 0） |
| 42 | 8 | payload 长度 |
| 50 | 32 | payload 的 SHA-256 |
| 82 | 64 | Ed25519 签名，消息为第 0–81 字节后接 payload；不签名时为 64 个 0 |
| 146 | | payload |

- payload 为空的文件是**撤回**：应用它的设备会删除当前补丁。
- **序号**默认是封装文件时的 Unix 时间（秒），也可以用 `publish --seq` 指定。设备只接受序号大于所有已接受文件的文件。
- **文件名**是 `<version_code>-<flavor>-<channel>-<abi>.fptc`，例如 `7-default-production-arm64-v8a.fptc`。`patch` 和 `publish` 按这个规则命名，设备上 `FlutterPatcher.patchTarget` 给出的 `fileName` 与之相同，App 或它的服务端据此挑选文件。
- 文件最大 320 MiB。

## 安全模型

只有一把密钥，即**补丁密钥**，而且是可选的：

- **签名宿主**（构建时 `flutter_patcher.yaml` 的 `trust.patch` 写有公钥）：设备只安装用这把密钥签名的文件。存储、CDN、传输链路以及 App 获取文件的方式都**不需要可信**：被篡改的内容只会校验失败。这也是开发时 `serve` 可以用明文 HTTP 的原因。
- **不签名宿主**（没有密钥，`build` 打印 `WARNING: UNSIGNED`）：签名区被忽略，能把文件交给 App 的一方就能在 App 中执行代码。内置下载器只接受 HTTPS，以及供 `serve` 使用的、指向设备本机的明文 HTTP；App 自行获取文件时，传输安全由 App 负责。不签名宿主同样接受签过名的文件。

私钥从不进入项目。`publish` 用它签名，`patch` 找得到时也会用；私钥来自 `--key-file`（仅 publish）、环境变量 `FLUTTER_PATCHER_KEYS`、`signing.command` 或你电脑上的密钥库，见 [CLI 参考](cli-zh.md)。构建宿主不需要私钥。

补丁私钥丢失后，用它构建的宿主再也收不到新补丁；泄露后，持有者可以为这些宿主签发文件。两种情况都需要用新密钥构建并发布新的商店版本：已发布宿主中的公钥无法更换。

设备每次安装文件，原生代码都会检查：

1. 文件大小与文件头一致且不超过 320 MiB，魔数和版本是 FPTC v1；
2. 指纹是本宿主的，其他 App、版本、flavor、渠道、ABI 或构建的文件都装不上；
3. payload 与 SHA-256 一致；签名宿主还要求签名能用宿主的公钥验证通过；
4. 序号大于设备已接受的最大序号（补丁和撤回都算），旧文件无法被重放回来；
5. 该补丁不在设备的黑名单中。

再次应用已安装的同一个文件会成功，且不改变任何状态。任何一项不通过，都不会安装。每次冷启动加载前，设备还会再检查一遍已安装的补丁：字节码宿主按上面的规则检查整个文件，SO 宿主检查解包后的文件与安装时校验过的内容是否一致。

## 设备上的生命周期

```text
App 拿到文件   来自自家接口、某个 URL（checkUpdate / applyPatch）、推送、内嵌文件……
     ↓
应用           原生代码校验整个文件 → 写入磁盘并原子提交；撤回文件则删除已安装的补丁
     ↓
（App 继续运行原来的代码）
     ↓
下次冷启动     再次检查已安装的补丁 → 加载补丁 → 首帧绘制后标记启动成功
     ↓
启动失败       达到阈值后自动退回安装包自带的版本，并把该补丁加入黑名单
```

- 补丁**不会**替换正在运行的代码；新补丁和撤回都在下次冷启动时生效。
- 安装是原子的：断电或进程被杀不会留下半个补丁。
- `rollback()` 只删除本设备上已安装的补丁，不拉黑，已接受的最大序号保持不变，之后只能安装更新的文件。
- 用户升级 App 后，旧版本的补丁会自动失效。
- 曾运行 1.0 宿主的设备，在第一次作为 1.1 宿主启动时删除 1.0 留下的签名清单状态（Android 的 `noBackupFilesDir/flutter_patcher_auth/`，iOS 的 `Application Support/flutter_patcher/auth/`）。
- 启动失败的判定和回滚细节见[崩溃保护](crash-protection-zh.md)。

## 能更新什么

| 改动 | 能否热更 | 原因 |
|---|:---:|---|
| 自己的 Dart 代码 | ✅ | |
| 纯 Dart 依赖 | ✅ | 字节码策略下由 whole 档携带 |
| 新增或修改资源（图片、字体、JSON 等） | ✅ | 引擎从补丁中读取资源，未修改的资源仍从安装包读取 |
| 删除资源 | ❌ | 补丁只能覆盖资源，不能删除 |
| 宿主引擎不支持安装补丁资源时的资源改动 | ❌ | 用旧版引擎构建的宿主没有这项能力，需要重新构建宿主 |
| 原生代码、原生插件、构建脚本 | ❌ | 补丁只包含 Dart 代码和资源 |
| 带原生能力的依赖 | ❌ | 它们与原生代码绑定，只能随新版本更新 |
| 依赖上述包的包（字节码策略） | ❌ | 它们和所依赖的包一起留在宿主中 |
| 被修改的代码调用 FFI（字节码策略） | ❌ | 解释器不能执行 FFI 调用 |
| 运行时动态构造的 `IconData`（字节码策略） | ❌ | 补丁中的图标字体只保留用到的常量图标 |
| Flutter SDK 版本 | ❌ | 补丁必须使用与宿主相同的 Flutter 版本生成 |

这些限制在 `patch` 时检查，违反时直接报错，不会把有问题的补丁发到用户手机上。还有几种情况补丁可以照常生成，但部分改动可能不生效，`patch` 会给出警告：

- **原生代码读取了被修改的资源**：原生代码通过系统接口读取的仍是安装包里的旧资源。
- **代码运行在另一个 Flutter 引擎中**：例如后台任务、推送回调启动的入口函数，可能运行旧代码或使用旧资源。
- **补丁资源过大**（超过 16 MB）：补丁资源会在进程存活期间常驻内存。

各项对应的错误码见[错误码与排障](troubleshooting-zh.md)。

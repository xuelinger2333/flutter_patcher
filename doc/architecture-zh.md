# 工作原理

[English](architecture.md) | **简体中文**

> 理解什么是宿主、补丁如何基于基线生成、设备如何决定是否安装一个补丁文件，以及补丁能携带哪些改动。

你已经跑通了第一个补丁，或者正在判断 flutter_patcher 是否适合你的 App。本页说明机制和限制，不列命令和选项（见 [CLI 参考](cli-zh.md)），也不列 Dart API（见 [API 参考](api-reference-zh.md)）。

## 三个角色

```text
  开发机（CLI）                   下发                              用户设备（插件）
 ────────────────              ──────────────────────           ──────────────────
 build  → 宿主 + 基线                                            安装的是 build 产出的宿主
 patch  → 一个 .fptc 文件 ──→   HTTPS 服务、自家接口、     ──→  checkUpdate / applyPatch
 publish → .fptc 写入存储        推送消息、内嵌文件                或 applyPatchBytes / applyPatchFile
                                                                        │
                                                              校验、安装；下次冷启动加载
```

| 角色 | 职责 |
|---|---|
| 开发机 | `dart run flutter_patcher build` 构建宿主及其基线。`patch` 把此后的每次改动生成为一个补丁文件，例如 `1-arm64-v8a.fptc`。可选的 `publish` 把该文件写入存储（本地目录或 S3）；`serve` 把它提供给调试设备 |
| 下发 | 内置下载器（`checkUpdate` 与 `applyPatch`）从 URL 获取文件。App 也可以通过自己的渠道获取文件，再交给 `applyPatchBytes` 或 `applyPatchFile`，见[自定义下发](advanced-zh.md#由自家服务端自定义下发) |
| 设备 | 原生代码校验文件后安装，并在下次冷启动时加载 |

**基线存储**保存每个已发布版本的构建记录，只有 CLI 读取它。

## 宿主：能接收补丁的安装包

补丁只能安装到用 `flutter_patcher build` 构建的安装包上，这类安装包称为**宿主**，因为普通的 `flutter build` 产物中没有加载补丁的代码。与普通构建相比，宿主包含：

1. **flutter_patcher 引擎**：在官方 Flutter 引擎的基础上增加了加载补丁所需的能力。CLI 按你所用的 Flutter 版本下载并校验该引擎。
2. **生成的启动入口**：在 `main` 之前运行，负责加载已安装的补丁。
3. **宿主策略**：这次构建的身份信息和可选的补丁公钥。

| 宿主策略字段 | 内容 |
|---|---|
| `application_id`、`version_code` | 包名（iOS 为 bundle id）与构建号 |
| `flavor`、`channel` | 默认为 `default` 与 `production` |
| `abi` | `arm64-v8a` 或 `ios-arm64` |
| `strategy` | `bytecode` 或 `so` |
| `fptc_key` | 补丁公钥；不签名宿主为 `-` |

`build` 把宿主策略连同编译指纹写入安装包（APK 中的 `assets/flutter_patcher/host-trust.json`，iOS 为 Info.plist）。设备依据宿主策略判断每个补丁文件。宿主策略是已发布安装包的一部分，所以宿主始终保持构建时的签名方式和公钥，之后新增的密钥只对此后构建的宿主生效。

在 Android 上，宿主在 Android 9（API 28）及以上版本、App 的主进程中加载补丁。更早的版本按原安装包运行，因为宿主在那里拒绝加载补丁。

## 两种补丁策略

Flutter release 包中的 Dart 代码被编译为机器码。flutter_patcher 提供两种更新方式：

| | 字节码（默认） | SO |
|---|---|---|
| 补丁内容 | 你的应用自己的包（其中用到的代码）编译成的字节码；whole 层级还包含纯 Dart 依赖 | 整个重新编译的 `libapp.so` |
| 运行方式 | 引擎内置的解释器执行补丁携带的全部代码；Flutter、插件和补丁不携带的包仍以安装包中的机器码运行 | 启动时由 Flutter 加载补丁中的 `libapp.so`，代替安装包中的版本 |
| 平台 | Android、iOS | 仅 Android |
| 补丁体积 | 小，只有你的应用代码，不含 Flutter 和插件 | 大，与 `libapp.so` 相当 |
| 补丁代码的运行速度 | 补丁携带的代码全部解释执行，比机器码慢 | 与原版相同 |

iOS 宿主使用字节码，因为 iOS 不允许加载下载的机器码。Android 在构建时选择策略（SO 策略用 `build android --strategy so`），该版本的所有补丁都沿用这一策略，因为宿主只能加载构建时选定的那种补丁。

字节码补丁分为两个层级，由 `patch` 自动选择：

- **lean**：包含你的应用自己的包，优先使用；
- **whole**：同时包含纯 Dart 依赖，在其中有依赖发生变化或 lean 无法承载改动时使用。

## 基线：补丁与谁对比

补丁是当前代码与用户手机上版本之间的差异，所以 CLI 必须精确掌握后者。`build` 在打包的同时把该版本的完整记录保存为**基线**：编译结果、源码哈希、依赖、资源、宿主策略，以及构建所用的引擎和工具版本。

`patch` 按 flavor 和构建号（Android 为 versionCode，iOS 为 CFBundleVersion）找到对应的基线，与当前源码对比，只打包变化的部分。

| 规则 | 作用 |
|---|---|
| 只新增，不覆盖 | 同一构建号构建出不同内容时，`build` 报 `BASELINE_RELEASE_CONFLICT`，因为已发出去的 App 会匹配不上自己的基线。发布新内容需要提升构建号 |
| 工具版本固定 | 一个版本的所有补丁都使用其基线记录的引擎和工具版本，所以 flutter_patcher 发布新引擎后，已上线的版本仍能打补丁 |

基线丢失后，该版本无法再生成补丁，因为没有任何记录说明用户正在运行什么；这些用户需要通过新的商店版本获得修复。基线的保管方式见[保管基线](production-playbook-zh.md#2-保管基线)。

## 补丁文件

补丁文件（FPTC v1）由 146 字节的文件头和其后的 payload（补丁 ZIP）组成。补丁文件需要 flutter_patcher 1.1.0 或更新版本；用 flutter_patcher 1.0.0 构建的宿主用 flutter_patcher 1.0.0+1 打补丁，见[从 1.0 升级](upgrading-zh.md)。字节布局与命名规则见[补丁文件](cli-zh.md#补丁文件)。

| 文件头字段 | 用途 |
|---|---|
| 宿主指纹 | 文件所属的唯一宿主构建 |
| 序号（`seq`） | 封装文件时的 Unix 时间（秒），也可以用 `publish --seq` 指定。设备只接受序号大于所有已接受文件的文件 |
| payload 的 SHA-256 | 识别损坏或被篡改的 payload |
| Ed25519 签名 | 证明文件由补丁密钥签名；不签名时为全 0 |

- payload 为空的文件是**撤回文件**：应用它的设备会删除当前补丁。
- 每个宿主构建只有一个文件名，例如 `7-arm64-v8a.fptc`，所以新补丁或撤回文件会替换之前的文件。设备上 `FlutterPatcher.patchTarget` 的 `fileName` 给出同一个文件名。
- 文件最大 320 MiB。

## 安全模型

签名只使用一把密钥，即**补丁密钥**。开启签名后，存储、CDN、传输链路以及 App 获取文件的方式都无须可信，因为被篡改的文件无法通过校验。

| 宿主 | 安装哪些文件 |
|---|---|
| 签名宿主（构建时 `flutter_patcher.yaml` 的 `trust.enabled` 为 `true`） | 只安装用这把密钥签名的文件 |
| 不签名宿主（`build` 打印 `WARNING: UNSIGNED`） | 安装属于本宿主的任何完整文件，无论是否签名。能把文件交给 App 的一方即可在 App 中执行代码，所以下发渠道必须可信。内置下载器只接受 HTTPS，以及供 `serve` 使用、指向设备本机的明文 HTTP；使用自定义下发时，渠道安全由 App 负责 |

在要发布的那次构建之前开启签名的方法见[开启签名](production-playbook-zh.md#3-开启签名)。私钥不进入项目：`patch` 和 `publish` 从密钥包、环境变量、签名命令或本机密钥库中获取私钥，见[私钥从哪里来](cli-zh.md#私钥从哪里来)。`build` 只需要公钥。

> **警告：已发布宿主中的公钥无法更换**
>
> 私钥丢失后，用它构建的宿主无法再接收新的补丁文件。私钥泄露后，持有者可以为这些宿主签发文件。两种情况都需要用新密钥构建并发布新的商店版本。

设备每次安装文件时，原生代码检查：

1. 文件大小与文件头一致且不超过 320 MiB，魔数和版本为 FPTC v1；
2. 指纹属于本宿主，所以其他 App、版本、flavor、渠道、ABI 或构建的文件无法安装；
3. payload 与 SHA-256 一致；签名宿主还要求签名能用宿主公钥验证通过；
4. 序号大于设备已接受的最大序号（补丁和撤回文件均计入），所以旧文件无法被重放；
5. 该补丁不在设备的黑名单中。

任何一项不通过，都不会安装；各种情况的结果见[设备接受哪些文件](api-reference-zh.md#设备接受哪些文件)。每次冷启动加载已安装的补丁之前，设备会再次检查：字节码宿主按上述规则检查整个文件，SO 宿主检查解包后的文件与安装时校验过的内容是否一致。

## 设备上的生命周期

```text
App 获取文件   通过内置下载器（checkUpdate / applyPatch）
               或自定义下发（applyPatchBytes / applyPatchFile）
     ↓
应用           原生代码校验整个文件 → 写入磁盘并原子提交；撤回文件则删除已安装的补丁
     ↓
（App 继续运行当前的代码）
     ↓
下次冷启动     再次检查已安装的补丁 → 加载补丁 → 首帧绘制后标记启动成功
     ↓
启动失败       达到阈值后退回安装包自带的版本，并把该补丁加入黑名单
```

- 新补丁和撤回文件都在下次冷启动时生效，因为正在运行的进程保持它已加载的代码。
- 安装是原子操作：断电或进程被终止后，设备上要么是之前的状态，要么是新的状态。
- 用户升级 App 后，旧版本的补丁不再生效，因为指纹变了；新版本需要单独的补丁。
- 启动失败的判定与回滚见[崩溃保护](crash-protection-zh.md)。

## 能更新什么

| 改动 | 能否热更 | 原因 |
|---|:---:|---|
| 自己的 Dart 代码 | ✅ | |
| 纯 Dart 依赖 | ✅ | 字节码策略下由 whole 层级携带 |
| 新增或修改资源（图片、字体、JSON 等） | ✅ | 引擎从补丁中读取这些资源，未修改的资源仍从安装包读取 |
| 删除资源 | ❌ | 补丁只能覆盖资源，不能删除 |
| 宿主引擎不支持安装补丁资源时的资源改动 | ❌ | 用旧版引擎构建的宿主不具备这项能力，需要重新构建宿主 |
| 原生代码、原生插件、构建脚本 | ❌ | 补丁只包含 Dart 代码和资源 |
| 带原生能力的依赖 | ❌ | 它们与原生代码绑定，只能随新版本更新 |
| 依赖上述包的包（字节码策略） | ❌ | 它们与所依赖的包一起保留在宿主中 |
| 补丁携带的包中有 FFI 调用（字节码策略） | ❌ | 补丁携带整个包，而解释器不能执行 FFI 调用；把 FFI 调用放在保留在宿主中的包里，例如插件 |
| 运行时动态构造的 `IconData`（字节码策略） | ❌ | 补丁中的图标字体只保留用到的常量图标 |
| Flutter SDK 版本 | ❌ | 补丁必须用与宿主相同的 Flutter 版本生成 |

`patch` 检查以上限制，改动超出限制时失败并给出错误码。以下情况补丁照常生成，但 `patch` 给出警告，因为部分改动不会生效：

| 警告 | 情况 |
|---|---|
| `PATCH_NATIVE_ASSET_READER` | 原生代码通过系统接口读取被修改的资源时，读到的仍是安装包中的原始资源 |
| `PATCH_BACKGROUND_ENTRY` | 运行在另一个 Flutter 引擎中、且补丁没有携带的入口函数（例如后台任务、推送回调启动的入口）运行的是安装包中的原始代码 |
| `PATCH_RESOURCE_SIZE` | 补丁资源超过 16 MB，在进程存活期间常驻内存 |

全部错误码与警告码见[错误码与排障](troubleshooting-zh.md)。

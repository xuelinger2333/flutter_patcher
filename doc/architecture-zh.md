# 工作原理

[English](architecture.md) | **简体中文**

本文解释 flutter_patcher 为什么能工作、为什么值得信任，以及它的边界在哪里。只讲概念，不讲命令用法（见 [CLI 参考](cli-zh.md)）。

## 三个角色

```text
  开发机（CLI）                存储                         用户设备（插件）
 ────────────────           ───────────                 ──────────────────
 build  → 安装包 + 基线  ──→  基线存储
 patch  → 补丁                                        安装的是 build 产出的包
 publish → 签名清单 + 补丁 ──→ 发布存储 ──(HTTPS)──→  checkUpdate / applyPatch
                                                             │
                                                     下次冷启动加载补丁
```

- **开发机**：`dart run flutter_patcher` 负责构建安装包、生成补丁、签名和发布。
- **存储**：两类。**基线存储**保存每个已发布版本的构建记录，只有开发机使用；**发布存储**保存补丁和清单，由你的 HTTPS 服务或 CDN 对外提供下载。
- **设备**：插件下载补丁，在原生代码中逐项校验后安装，下次冷启动时加载。

## 宿主：能接收补丁的安装包

补丁只能装到用 `flutter_patcher build` 构建的安装包上，这样的安装包称为**宿主**。与普通的 `flutter build` 相比，宿主多了三样东西：

1. **flutter_patcher 提供的 Flutter 引擎**：在官方引擎的基础上增加了加载补丁所需的能力。CLI 按你的 Flutter 版本下载并校验它，你使用的 Flutter SDK 不会被修改。
2. **一个生成的启动入口**：在你的 `main` 之前运行，负责在冷启动时把补丁装进来。你的源码不会被修改。
3. **宿主策略**：写进安装包的身份信息和公钥，包括包名、版本号、flavor、渠道、ABI、补丁策略和三把公钥。安装包签名之后，宿主策略就无法再被改动，设备以它为准判断哪些补丁可以接受。

在 Android 上，宿主只在 Android 9（API 28）及以上、App 的主进程中加载补丁；更早的设备上按原包运行。

## 两种补丁策略

Flutter release 包中的 Dart 代码会被编译成机器码。flutter_patcher 提供两种方式更新它：

| | 字节码（默认） | SO |
|---|---|---|
| 补丁内容 | 改动部分编译成的字节码模块 | 整个重新编译的 `libapp.so` |
| 运行方式 | 引擎内置的解释器执行补丁中的代码，未改动的代码仍以机器码运行 | 启动时让 Flutter 改为加载补丁中的 `libapp.so` |
| 平台 | Android、iOS | 仅 Android |
| 补丁体积 | 小，只包含改动 | 大，与 `libapp.so` 相当 |
| 被修改代码的运行速度 | 解释执行，比机器码慢 | 与原版相同 |

iOS 不允许加载下载的机器码，因此只能使用字节码。Android 在 `build` 时选择策略，之后该版本的所有补丁都沿用这个选择。

字节码补丁有两档，由 `patch` 自动选择：**lean** 只包含你自己的包，优先使用；当依赖发生变化，或 lean 档无法满足时，改用 **whole**，把可热更的依赖一起带上。

## 基线：补丁与谁对比

补丁是"当前代码"与"用户手机上的版本"之间的差异，因此必须精确知道后者是什么。`build` 在打包的同时把这个版本的完整事实保存为**基线**：编译结果、源码哈希、依赖、资源、公钥，以及构建所用的引擎和工具版本。

`patch` 按 flavor 和版本号（Android 的 versionCode，iOS 的 CFBundleVersion）找到对应的基线，再与当前源码对比，只打包变化的部分。

基线有两条规则：

- **只新增，不覆盖**。同一个版本号如果构建出不同的内容，`build` 会拒绝，而不是悄悄替换已发布版本的记录。要发布新内容，请提升版本号。
- **工具版本固定**。基线记录了构建时使用的引擎和工具版本，以后为这个版本生成补丁时，始终使用同一套。即使 flutter_patcher 之后发布了新的引擎，已上线的版本也能继续打补丁。

由此可以推出：**基线丢失，该版本就无法再生成补丁。**

## 安全模型

`keys init` 生成三对 Ed25519 密钥：

| 密钥 | 签名对象 | 泄露的后果 |
|---|---|---|
| `patch` | 补丁包本身 | 需要发布新的宿主 |
| `publisher` | 发布清单：哪个版本应该安装哪个补丁 | 可以用 root 密钥更换，不需要发新版 |
| `root` | 更换 publisher 公钥的信任更新 | 需要发布新的宿主 |

三把**公钥**记录在 `flutter_patcher.yaml` 中，在 `build` 时写入宿主策略。**私钥**从不进入项目，只有 `publish` 和 `trust sign` 会用到，它们来自你电脑上的密钥库、CI 的 secret 或签名服务。生成补丁不需要任何私钥。

设备每次安装补丁，原生代码都会检查：

1. 清单由宿主信任的 publisher 签名；
2. 清单的范围正好对应这个宿主：包名、版本号、flavor、渠道、ABI、策略，以及编译指纹；
3. 补丁的大小、哈希与清单一致，补丁本身由 patch 密钥签名；
4. 补丁发布序号大于设备已接受的最大序号，旧补丁无法被重放回来；已撤回的序号无法再次生效。

任何一项不通过，补丁都不会被安装。因此存储、CDN 和传输链路都**不需要可信**：被篡改的内容只会导致校验失败。这也是开发时的 `serve` 可以用明文 HTTP 的原因，它只改变了传输方式，验证一项都没有少。

## 设备上的生命周期

```text
checkUpdate   下载本宿主对应的清单，在原生代码中校验；有新内容才返回 hasUpdate
     ↓
applyPatch    下载补丁 → 校验 → 写入磁盘并原子提交
     ↓
（App 继续运行原来的代码）
     ↓
下次冷启动    再次确认补丁仍然有效 → 加载补丁 → 首帧绘制后标记启动成功
     ↓
启动失败      达到阈值后自动退回安装包自带的版本，并把该补丁加入黑名单
```

- 补丁**不会**替换正在运行的代码，只在冷启动时生效。
- 安装是原子的：断电或进程被杀不会留下半个补丁。
- 用户升级 App 后，旧版本的补丁会自动失效。
- 启动失败的判定和回滚细节见[崩溃保护](crash-protection-zh.md)。

## 能更新什么

| 改动 | 能否热更 | 原因 |
|---|:---:|---|
| 自己的 Dart 代码 | ✅ | |
| 纯 Dart 依赖 | ✅ | 字节码策略下由 whole 档携带 |
| 新增或修改资源（图片、字体、JSON 等） | ✅ | 引擎从补丁中读取资源，未修改的资源仍从安装包读取 |
| 删除资源 | ❌ | 补丁只能覆盖资源，不能删除 |
| 宿主引擎不支持安装补丁资源时的资源改动 | ❌ | 用旧版引擎构建的宿主没有这项能力，需要重新构建宿主 |
| 原生代码、原生插件、构建脚本 | ❌ | 补丁只包含 Dart 代码和资源 |
| 带原生能力的依赖 | ❌ | 它们与原生代码绑定，只能随新版本更新 |
| 依赖上述包的包（字节码策略） | ❌ | 它们和所依赖的包一起留在宿主中 |
| 被修改的代码调用 FFI（字节码策略） | ❌ | 解释器不能执行 FFI 调用 |
| 运行时动态构造的 `IconData`（字节码策略） | ❌ | 补丁中的图标字体只保留用到的常量图标 |
| Flutter SDK 版本 | ❌ | 补丁必须使用与宿主相同的 Flutter 版本生成 |

这些限制在 `patch` 时检查，违反时直接报错，不会把有问题的补丁发到用户手机上。还有几种情况补丁可以照常生成，但部分改动可能不生效，`patch` 会给出警告：

- **原生代码读取了被修改的资源**：原生代码通过系统接口读取的仍是安装包里的旧资源。
- **代码运行在另一个 Flutter 引擎中**：例如后台任务、推送回调启动的入口函数，可能运行旧代码或使用旧资源。
- **补丁资源过大**（超过 16 MB）：补丁资源会在进程存活期间常驻内存。

各项对应的错误码见[错误码与排障](troubleshooting-zh.md)。
